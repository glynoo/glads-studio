# 架构与迭代边界

## 为什么选择 Golden20

用户将首阶段调整为大学生课题的简单可运行系统。四个交付 ZIP 已通过 SHA256；03 包有 20 个原图、20 个精确融合掩码和 58 张已生成的 Big-LaMa 参考候选。交付包不含学生修复模型的最终 `best.pt`，所以这一阶段采用真实参考图完成**人工复核流程**，不接新图推理。第 6、9 例的 R12 候选在清单中为空，显示“未生成”。

## 数据流

```text
交付包 03 ZIP ──只读、启动时验 SHA256──> 本地 Python 服务 ──JSON/图片──> React 页面
                                         │                         │
上传图片 ────────────────────────────────┤                         │
                                         ├──SQLite 账号、会话、素材索引与追加复核记录
                                         ├──上传图片目录
                                         └──ZIP 导出 CSV + 案例索引
```

所有图片路径由服务端预先建立的案例和资源 ID 白名单解析。浏览器只能请求 `/api/cases/{case_id}/images/{image_id}`，不能发送本机文件路径。交付包不会解压进前端，也不会被修改。

本地 SQLite 记录 `users`、`sessions`、`uploads`、`annotations` 和 `review_events`。密码使用 PBKDF2-SHA256 加盐保存，会话使用 HttpOnly cookie。人工记录自动绑定登录账号及候选 SHA256。每次人工结论追加事件，列表只把最后一条作为当前状态；历史可以回看。未提交表单保存在浏览器的 `glads-reference-draft:{case_id}`。上传图片存放在独立目录，索引保存图像 SHA256 和来源信息。

## 对应交付包

- 复核结论使用 `approve`、`reject`、`secondary_repair_required`、`defer_expert` 四种原始状态。
- 把算法生成候选与人工批准分开；Golden20 中所有案例均要求人工视觉复核。
- 来源与候选 SHA256 沿用 `lama_rescue_manifest.jsonl`，掩码外像素数显示为交付清单的记录，不由 UI 重算。
- 本地 API 是支持 Golden20 复核的最小服务，`POST /api/cases/{id}/reviews` 增加 `candidate` 字段以绑定具体候选。它不宣称已经实现交付包中的任务队列、完整 OpenAPI 或正式服务。

## 后续扩展点

1. 算法组提供经过验收的模型及稳定 CLI/任务服务后，在后端增加 job、run 与结果目录的适配；前端图像组件仍按 URL 查看原图、掩码和候选。
2. 多人远程协作阶段再设计角色权限、管理员操作、备份与部署流程；本地账号身份已经绑定复核记录。
3. 首页、素材池、复核记录和设置分别作为独立页面实现，共用 `reviewApi`、案例 ID 链接与少量页面容器。
4. 正式导出需包含任务运行记录、模型哈希、日志和审批链；当前导出覆盖 Golden20 参考案例的人工记录。
